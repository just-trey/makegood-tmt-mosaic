# Working in this repo

Recurring workflows live in `.claude/skills/`. Use the skill instead of
rebuilding its steps from memory.

## Before opening a PR

- Run the `ship-it` skill: the seven CI gates that block merge, plus the four
  docs that drift silently.
- `/code-review` is **required** on every PR that changes code. Only a
  prose-only diff (docs, CHANGELOG, comments) is exempt. Scripts and config
  count as code.
- Round count, stop rule and the six guards live in `ship-it` step 3. Load it
  before round 1. Short version: review before pushing, again after acting on
  findings, stop when a round returns taste instead of wrong output.

## Git workflow

- `main` is protected: PRs and green CI required; no direct push, force-push
  or branch deletion.
- Branch off `main`. One focused change per branch and PR.
- Semver, pre-1.0 (`0.x.y`). Read
  [CONTRIBUTING.md](CONTRIBUTING.md#versioning) before calling a change
  PATCH, MINOR, or MAJOR.

## Code conventions

- TypeScript `strict` is on. Don't weaken it to make something compile.
- UI copy follows [docs/ui-conventions.md](docs/ui-conventions.md)
  (vocabulary table, conventions 1-6, plain language 33-37): short sentences,
  each doing one job. `npm run check:copy` gates the shape. Docs are exempt.
- **Plain language is the bar for every user-facing string, and it is not a
  reading-age rule.** The reader runs a slicer daily. A word from Bambu
  Studio's UI or a Printables thread is free (filament, layer height, prime
  tower, tileable); a word that is ours goes (quantize, boolean, cut solid,
  viewBox).
  - Their words, real numbers. Never drop a measurement to sound friendlier.
  - Never explain a word they already own.
  - Removing jargon must not lengthen the sentence. Cut the explanation
    instead.
  - Substitutions live in conventions 33-37; `ship-it` step 2b checks them.
- **Before changing what a shared value means** (`colorSettings`, a depth, a
  placement), open every reader of it, not just the one you are editing.
  PR #113: a typed `0` made meaningful in `src/ui/colorList.ts` was still
  "unset" in `src/geometry/assembly.ts`, and a depth clamped there was
  discarded by `resolveCutDepth`.
- **A tolerance is not a user-facing value.** `0.02mm` keeps a boolean
  well-defined; told to a user as their recess depth, it slices to nothing
  and still costs an AMS slot. Any number shown to a user must make sense on
  a printer.
- **A special case that reaches across a boundary means the model is wrong
  further up.** Example: `if (part.cutThrough)` in code that should not know
  how parts cut.
- Don't add comments or docs describing the change you just made. The commit
  message is the changelog.

## Comments

- Explain **why**, never **what**. Default is zero comments; each must record
  a non-obvious decision, constraint, or gotcha. Worked examples:
  [src/turf.d.ts](src/turf.d.ts), the retry logic in
  [src/geometry/regions.ts](src/geometry/regions.ts).
- One line where possible. Docstrings 2-4 lines max, only for real
  constraints.
- Em dashes and long sentences are fine in comments.
- Never: banners/dividers, changelog-style comments, restated type
  signatures, narrated control flow.
- Preserve comments documenting intentional approximations, known
  limitations, or "this looks wrong but isn't".

## Audience

Hobbyist printer owners and MakeGood volunteers, not CAD users. Full framing:
[docs/audience.md](docs/audience.md).

- They know their slicer, not Fusion or mesh editing. A feature that needs
  CAD literacy is a bug.
- **Success measure**: a first-time volunteer reaches a printable,
  correctly-colored 3MF without touching a 3D modeling tool.
- When two options both work, ship the simpler workflow.

## Docs

One destination per topic. Don't split a topic across two. Rules for each
`docs/` destination load from [docs/CLAUDE.md](docs/CLAUDE.md); read it before
closing a tech-debt item or writing a findings report.

- **README**: orientation only (what, how to run, how it works, limits). Under
  ~200 lines.
- **docs/audience.md**: who it's for, the success measure. Read before filing
  or acting on a UX or workflow finding.
- **docs/pipeline.md**: how the geometry works. Read before touching
  `src/geometry/` or `src/export/`.
- **docs/ui-conventions.md**: numbered behavior rubric for anything
  user-facing.
- **`design-system/`**: color, type, spacing, radius, states, component specs.
- **docs/system-audit.md**: generated by the `system` lens, never authored.
- **docs/analytics.md**: the event catalog.
- **docs/tech-debt.md**: open deferred work and known-wrong behavior.
- **`docs/findings/`**: one dated report per driven investigation.
- **`docs/review-cycles/`**: one dated file per `/review-cycle` run.
- **`docs/spikes/`**: one write-up per throwaway prototype.
- **DECISIONS-NEEDED.md**: per-run inbox (below).
- **docs/troubleshooting.md**: one section per user-visible warning string.
- **docs/roadmap.md**: ideas not yet built.
- **CHANGELOG.md**: what changed per release, nothing else.

**Before touching boolean or polygon code**: `@turf/turf` is pinned to `6.5.0`
on purpose. Read docs/tech-debt.md first for why and what an upgrade takes.

### DECISIONS-NEEDED.md

A per-run inbox, never a document. An agent that cannot decide something
appends an entry answerable in one line, skips the item, and continues.
Before merge the file drains to empty and is deleted. Each entry ends as:

- **Resolved**: the answer becomes a comment next to the code it constrains.
- **Promoted**: it was a finding, not a decision; it goes to `tech-debt.md` or
  `roadmap.md`.
- **Still open**: the branch is not done. An unresolved entry is a blocker,
  not a footnote.

A decision is something only a human can settle. If everything drained by
promotion, check nothing needing a human went with it.

### Writing style

Applies to every doc above and `docs/` generally.

- Working notes for the owner and Claude. Optimize for scanning.
- First line states the result or decision; detail follows.
- Bullets over paragraphs. One fact per bullet. Sentences under ~20 words.
- Em dashes are fine.
- Record findings, numbers, caveats, decisions. Never narrate the reasoning
  journey, justify the doc, or editorialize.
- Bold key terms only, never whole sentences.
- Tables for anything with more than two data points.

## Planning

Every plan names, per work item, the model and the `/code-review` level, so
neither is re-litigated later.

- **Opus**: `src/geometry/`, `src/export/`, placement and scene math, anything
  where a wrong number ships a bad print.
- **Sonnet**: `src/ui/`, state plumbing, docs, config, test scaffolding.
- Split a PR across both when it has a geometry half and a UI half.
- Review levels: round 1 `high`, later code rounds `medium`, the single prose
  pass `low`. After a taste-only round, offer to skip further rounds.
- Verify by running the app, not only the tests.

## Code rules (check before finishing any change)

Judgment rules a linter cannot catch. Verify each explicitly; if one cannot
apply, say so in your summary.

1. **Never silently drop or skip user content.** Anything excluded from
   output (empty CSG result, mesh mismatch, failed op) gets a named warning
   saying what and why, even when excluding it is correct.
2. **Route new cases through the existing shared pipeline.** A new SVG
   element, export path or shape handler uses the same traversal, transform
   and exclusion logic. A one-off shortcut silently misses transforms and
   defs/clipPath exclusions.
3. **Failures degrade per-unit, not globally.** Catch a destructive failure at
   its color/part/shape boundary, report it for that unit, and finish the
   rest. One bad input never aborts or corrupts the export.
4. **No claims without a measurement.** No perf finding from code shape;
   benchmark on real sample files, else file it in tech-debt.md as
   "unmeasured". Every number in a PR body, commit, tech-debt section or
   findings report names the command that reproduces it. Unreproducible
   counts cost #240 and #241 a full review round each.

Mechanical rules live in lint/CI, not here: copy shape (`check:copy`),
troubleshooting quotes (`check:troubleshooting`), unsafe `any` and `parseInt`
radix (ESLint), formatting (Prettier). Numeric input guards are only partly
covered; `docs/tech-debt.md` says which part. Workflow rules live in the
review and ship skills.
