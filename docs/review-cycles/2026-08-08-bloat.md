## 1. Verdict

The geometry engine is not the problem, and this cycle says so with evidence: a full
end-to-end export (chair body, 3-color SVG, Bambu X1C) completed clean during the maker
pass, and **no Tier 0 correctness finding was raised by any of the three lenses**. Every
finding this cycle is about the surface in front of that engine. The "bloat" complaint
turns out to be literally measurable rather than a feeling — **1073px of forced scroll
past a 730px pane to reach Export on a 1440×810 laptop, with no artwork loaded at all**,
and **48 visible interactive controls on first paint** before the user has done anything.
Both trace to one cause: all six sidebar sections ship `<details class="sec" open>`
(verified in `index.html`), so the panel never reflects what the user has actually done.

**The one thing most worth doing:** collapse the sections that have nothing to act on yet.
It is a single mechanism, it is the direct cause of both headline measurements, and it
subsumes three other findings (Export-eager, Advanced framing, section-state memory)
without deleting a single capability.

## 3. Ranked action list

### Tier 0 — Correctness

None. Stated explicitly because it is the cycle's most reassuring result: three lenses
driving the real app end-to-end produced no wrong output, no data loss, and no silent
failure.

### Tier 1 — Maker (the arbiter)

**A1. All six sidebar sections are expanded regardless of workflow stage.** _(High)_
Lenses: `maker-workflow-review` #1, `subtract` F3.
Observation: 1440×810, Disc, no artwork — scrollHeight 1803 / clientHeight 730, i.e. 1073px
of overflow before Export is reachable. With sample artwork: 2284/730. Six
`<details class="sec" open>` in `index.html` confirmed as the cause. `subtract` independently
landed on the same mechanism from the Export end: the printer `<select>` and both export
buttons render fully on first paint, before any artwork or color exists to judge a printer by.
Violates `ui-conventions.md` conv. 8 in spirit — controls that act on a selection are present
with no selection.
Change: collapse Artwork fit / Depth / Colors detected / Export until at least one design
exists; keep Part and Artwork open since they are always actionable.
Effort: **S–M**.

**A2. Switching part shape carries artwork across with no confirmation.** _(High)_
Lens: `maker-workflow-review` #3.
Observation: loaded `sample-badge.svg` on the default Wheel, switched `#shape-kind` to `disc`
with no auto-accept hook installed — `#confirm-dialog` never opened, no native dialog fired,
and the artwork row was still present after the switch. Repeating Disc → Chair body with a
design bound to "All zones" touched off a rebuild still cycling 47%→93% after 190+ seconds
(software-rendered, so the _duration_ is not a production claim — the _sequence_ is: a
near-empty transitional viewport and, per existing tech-debt, no cancel).
Change: reuse the existing confirm-dialog pattern (already used for variant switches) before a
kind switch that will remap or discard loaded artwork.
Effort: **S–M**.

**A3. "Disc (reference)" sits in the primary Part picker at the same weight as four real parts.** _(High)_
Lens: `subtract` F1. See conflict **C1** — this item is the cycle's headline question.
Observation: live dropdown is `["Wheel (Top ×2 + Cap)", "Footrest", "Hubcap", "Chair body",
"Disc (reference)"]`. Disc produces a plain flat cylinder related to no TMT part; its only
explanation lives in the help dialog. `partPanel.ts` already excludes rect/round/STL from this
same list on the reasoning that "picking a real part shouldn't require navigating a second
nested dropdown" — Disc is the surviving exception, for arguably the same reason those were cut.
Change: pull Disc from the primary `<select>`; keep it reachable via `?kind=disc` using the
`AssemblyKind.hidden` machinery that already exists (`renderShapeKindOptions`, exercised by
`tests/persist-hidden-kind.test.ts`).
Effort: **S** (one-line option-list change plus a `?kind=disc` regression check).

**A4. "Advanced: per-part face & alignment" requires exactly the CAD literacy the audience doc rules out.** _(Medium)_
Lenses: `subtract` F2, `assumptions` F1 — independently, from different angles.
Observation: expanded live on the Wheel it renders `face detected: normal (0.00, 1.00, 0.00),
plane offset 24.25mm, 104-pt boundary`, a face-pick `<select>` reading `#1: area 29403mm²
(normal 0.00,1.0…)`, plus `pivot X`, `pivot Z`, `angle°`, `base thick.`. The help dialog's
full text was grepped for `Advanced`, `pivot`, `face normal`, `boundary`, `plane offset` —
**zero matches for any of them**. `docs/audience.md`: users "don't think in terms of meshes,
vertices, or UV unwraps" and "if a step requires CAD literacy, it's a bug in the tool."
Mitigating: `<details>`-closed by default, so the median session pays no screen cost.
Change: keep the capability (a real escape hatch for a bad or custom mesh) and fix the one
thing visible before it is opened — reword the summary so a non-CAD user knows they can skip
it with confidence. See conflict **C4**.
Effort: **S** (wording) / **M** (if each field gets a plain-language line + a help anchor).

**A5. "Load sample artwork" duplicates instead of replacing.** _(Low–Medium)_
Lens: `maker-workflow-review` #4.
Observation: clicking it with the sample already loaded adds a second fully-overlapping
`sample-badge.svg` row, immediately producing the overlap warning — from the single most
discoverable "try it" affordance in the panel, on an action a curious first-timer repeats.
Change: replace the existing sample row, or relabel/disable the button once loaded.
Effort: **S**.

**A6. "↻ Reload assembly" is a permanent row for a failure state neither lens ever saw.** _(Low)_
Lenses: `assumptions` F6, `subtract` F2 (as a sub-recommendation).
Observation: on every assembly kind driven (Wheel, Chair body) with every part showing ✓,
the button still renders as its own full-width row above the part checklist. Per
`assemblyPanel.ts` it exists for auto-load failure, but renders whether or not that happened.
Its effect is explained nowhere in the help dialog.
Change: show it only once a load has actually failed, next to the part that failed.
Effort: **S**.

**A7. Overlapping designs render as z-fighting, not as a signal.** _(Medium)_
Lens: `maker-workflow-review` #5.
Observation: two designs bound to the same Disc surface produce severe moiré/striping across
the overlap region in the viewport. The text warning is correct and specific; the picture
looks like the app broke — a worse signal for a no-CAD audience than a rendering artifact
should be.
Change: give the overlap region an explicit treatment instead of leaving raw geometry to
z-fight. Conv. 21 asks these be distinguishable by pattern/motion rather than hue, which the
current striping technically is — but it reads as breakage, not as meaning.
Effort: **M**.

**A8. A multi-zone part turns one template download into five files to hand-track.** _(Medium — research first)_
Lens: `assumptions` F3.
Observation: Wheel shows one "↓ Download design template (SVG)". Chair body shows "Design
templates (one per surface): Left side · Back · Front · Right side · Seat" — five separate
downloads, each drawn on, saved and re-uploaded independently, for one physical part.
Change: bundle as one multi-artboard SVG or a labeled `.zip`. **Gated on confirming Inkscape /
Illustrator / Affinity round-trip multi-artboard SVG cleanly** — that is the one thing that
could make this worse rather than better, and it is unverified.
Effort: **M**, plus a research spike before committing.

### Tier 2 — Usability

**B1. Viewport chrome collides with the gizmo.** _(Low–Medium)_ — `assumptions` F5.
At 1600×1000 with a selection frame active, the AMS-capacity pill's top edge and dismiss "×"

## 4. Conflict ledger

**C1 — Disc: make it the default, or take it out of the list?** _(the cycle's headline question)_

- `maker-workflow-review` #2 wants `#shape-kind` to **default to `disc`** on a fresh session,
  on the grounds that the app's real default (`asm:wheel`, verified against an empty-storage
  context — `localStorage` keys `[]`, restore banner hidden) is the heaviest object in the list
  and a poor first impression.
- `subtract` F1 wants Disc **removed from the picker entirely**, because it produces no TMT part
  and a volunteer who picks it cannot reach a printable device no matter how far they carry the
  session.
- **Resolution: `subtract` wins; the maker _observation_ stands but its _remedy_ loses.**
  Both lenses correctly identified that the first screen is too heavy. But the maker's fix would
  make a non-part the first thing every new volunteer sees, which fails `docs/audience.md`'s
  success measure ("reaches a printable, correctly-colored 3MF") more sharply than a heavy
  default does. The heavy-first-screen problem is real and is addressed by **A1** — conditional
  disclosure — which fixes it without pointing anyone at a shape that builds nothing.
- **Note on the arbitration rule:** the maker lens normally wins on priority and taste. Here it
  is overruled on _its own criterion_ — the audience contract — not on another lens's standard.
  Recorded prominently because it is the one place this cycle where the arbiter did not carry.

**C2 — Drag-to-merge colors: delete it, or protect it?**

- `subtract` F4 wants drag-to-merge **dropped**, keeping only the "Merge with…" dropdown: three
  paths to one operation, and the help text itself admits the redundancy ("both do the same
  thing"). It argues the dropdown is the more accessible of the two and already exists as the
  documented fallback.
- `maker-workflow-review` names drag-to-merge explicitly as a **strength**: "Direct manipulation
  in the viewport is a real strength — drag-to-merge colors, click-to-select … match slicer /
  Illustrator muscle memory. Nothing here needs to change."
- **Resolution: maker wins. Keep both.** This is taste and workflow, exactly what the arbiter
  arbitrates, and the maker lens is the only one reviewing against the actual users. `subtract`'s
  accessibility point survives as a real one — the dropdown must stay as the keyboard-reachable
  path — but it is an argument for keeping the dropdown, not for deleting the drag.

**C3 — Artwork fit sliders: do they earn their rows?**

- `assumptions` F2 counts 13 rendered controls for artwork placement (5 slider+number pairs,
  2 checkboxes, 1 button) and proposes testing whether the sliders earn their rows given the
  gizmo the help dialog names as primary.
- The maker lens raises no complaint about the sliders and praises the direct-manipulation model
  the argument leans on.
- **Resolution: no deletion. Downgraded to Tier 4.** The screen-space win `assumptions` is after
  is delivered by **A1** without removing a control — conditional collapse hides the whole
  section when there is no artwork, which is precisely when those 13 controls are pure cost.
  Deleting sliders that the maker lens did not flag is trading a capability for a win already
  available for free.

**C4 — The Advanced panel: reword it, or get it out of the shipped app?**

- `subtract` F2: **keep**, reword the summary, fold "↻ Reload assembly" behind the same
  disclosure.
- `assumptions` F1 goes further: it "reads like a part-authoring tool for whoever runs the
  `add-part`/`bake-zones` skills" and should possibly leave the shipped app entirely, the way
  `public/filaments.json` is already edited outside the UI (conv. 18).
- **Resolution: `subtract`'s position, recorded with `assumptions`' dissent.** The panel is a
  genuine recovery path for a bad or custom mesh, and removing it would leave a user with a
  mis-detected face no way out. But `assumptions` is right that nothing marks it as
  maintainer-territory, and it is right that zero of its five vocabulary terms appear anywhere
  in 2,444 words of help. Reword first (**A4**); revisit removal only if telemetry or a later
  cycle shows no end user ever successfully uses it.

## 5. Considered and not recommended

Recorded so the next cycle does not re-litigate them.

- **Delete drag-to-merge** (`subtract` F4) — lost C2 to the arbiter. Keep both paths.
- **Drop the artwork-fit sliders** (`assumptions` F2) — lost C3. A1 delivers the same screen-space
  win without removing a control.
- **Default the part picker to Disc** (`maker-workflow-review` #2) — lost C1. The underlying
  observation is actioned as A1 + A3 instead.
- **Move the Advanced panel out of the shipped app** (`assumptions` F1) — deferred per C4; reword
  first.
- **"Cut to artwork shape" (hubcap)** — `subtract` F5 measured it as _the single most
  explanation-expensive feature in the app_ (~300 words across 5 paragraphs of help, plus caveats
  in tech-debt and the README, for one checkbox on one part) and **explicitly recommends keeping
  it**: it is an audience-appropriate differentiator, and the fix is tightening the explanation,
  not removing the feature. Named here so a future subtraction pass does not rediscover the cost
  and reach the opposite conclusion.
- **Trimming the help dialog as its own task** — `subtract` F6 and `assumptions` F4 both measured
  it at 2,444 words / 8 sections, and `subtract` explicitly declines to act on the prose:
  CLAUDE.md is clear that docs follow the app. Length is a _symptom_. B3's duplication fix is the
  only help-text item in the action list.
- **Keyboard nudge / shortcut coverage** (`maker-workflow-review` #8) — Tier 4 quality-of-life.
  **But it carries one owed check, not a finding:** the maker pass did **not** exercise `Ctrl/Cmd+Z`,
  and conv. 22 ("undo covers anything done deliberately") is a standing commitment. Verifying it
  is a task for the next pass; nothing here claims it is broken.
- **Batch operations across zones** — the maker lens considered and rejected adding these itself:
  "select several zones and edit them as a set" approaches the CAD-literacy bar `docs/audience.md`
  rules out.

### Already tracked — confirmed still live, not re-filed

All three lenses independently checked `docs/tech-debt.md` before filing and dropped what was
already recorded. Confirmed present in this build: the 14-swatch unlabeled Body/blank color grid
(conv. 16–18), the body-color hint pointing at a different panel (conv. 4), the AMS-capacity
pill's three-remedies-at-once prose (conv. 3), the AMS slot cost rendering in both `#warnings` and
`#slot-count`, and the no-cancel long rebuild. These compound with A1 — a panel needing a paragraph
of help to use safely is also a panel expanded by default — but they need no new tech-debt sections.
